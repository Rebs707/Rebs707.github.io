Enterprise Knowledge Platform: Local-First Document Ingestion & Retrieval

A FastAPI-based document platform that accepts bounded UTF-8 text and Markdown uploads, extracts and chunks content, persists document metadata and chunks in SQLite, and retrieves matching excerpts through deterministic keyword scoring.

01. Project Overview

Enterprise Knowledge Platform is a local-first document ingestion and keyword-retrieval prototype. It provides a small API surface for accepting supported text documents, converting them into overlapping chunks, storing their metadata and content in SQLite, and retrieving matching chunks with source-document references.

The current release focuses on a complete, deterministic ingestion-to-retrieval path. It does not generate natural-language answers or claim semantic understanding of document meaning.

Project objectives

  • Define a bounded upload contract for UTF-8 plain-text and Markdown documents.
  • Normalize text and split longer content into overlapping retrieval chunks.
  • Persist document metadata, SHA-256 digests and chunks in a local SQLite database.
  • Provide keyword-based retrieval with deterministic scoring and result ordering.
  • Expose upload, metadata, search and health operations through FastAPI.
  • Validate normal and invalid-input behaviour through automated tests and local API smoke checks.

Prototype · Local runtime verified The application and its document workflow were exercised locally. Docker image and container runtime verification have not been performed for this release.

02. Problem Definition

Documents need a consistent path from ingestion to retrieval before more advanced knowledge capabilities can be added. Even a deliberately small first increment must handle file boundaries, text normalization, chunk creation, durable storage and traceable retrieval results.

Controlled ingestion

Uploads need explicit format, encoding and size boundaries so unsupported or malformed input is rejected predictably.

Retrieval-ready content

Longer documents need to be split into manageable chunks while retaining overlap between adjacent segments.

Traceable storage

Search results need to retain document identifiers and filenames so a matching excerpt can be traced to its source document.

Honest retrieval semantics

A first retrieval baseline can be useful without embeddings or an LLM, provided lexical matching is clearly distinguished from semantic search.

03. Architecture & System Design

The implemented path is a synchronous API workflow. The upload endpoint validates the filename, extension, size and UTF-8 content, then delegates text preparation to the document agent. The resulting chunks and document metadata are persisted in SQLite. Search tokenizes the query, scores stored chunks and returns a bounded ranked result set.

API surface

  • GET /health returns application health.
  • POST /documents accepts a multipart field named file and indexes supported .txt or .md content.
  • GET /documents/{document_id} returns stored document metadata and chunk count.
  • GET /search?q={query}&limit=10 searches indexed chunks.
  • GET /knowledge/{topic} is a compatibility alias for keyword search.
  • FastAPI provides interactive API documentation at /docs.

04. Core Components

DocumentAgent — ingestion preparation

Delegates supported-file validation, UTF-8 decoding and text normalization to the text-processing service, then creates overlapping chunks. The supported extensions are .txt and .md; UTF-8 BOM and CRLF line endings are normalized.

Text processing — validation and chunking

Rejects unsupported extensions, invalid UTF-8, empty content and null characters. The default chunk size is 900 characters with 120 characters of overlap. Chunk size and overlap are configurable at the function level, subject to the constraint that size is positive and overlap is smaller than size.

KnowledgeStore — SQLite persistence

Stores document identifiers, filenames, SHA-256 digests, upload timestamps, content types and chunk records. The default database path is data/knowledge.db, configurable through EKP_DB_PATH. Database writes group metadata and chunk inserts in a transaction.

SearchAgent and KnowledgeWorkflow — retrieval coordination

The SearchAgent calls the SQLite store and returns the query, result count and ranked results. KnowledgeWorkflow delegates its current retrieval operation to the same search agent. Knowledge-graph construction and recommendation agents are reserved placeholders and raise NotImplementedError.

06. Implementation Walkthrough

Phase 1 — Bounded document ingestion

The upload endpoint reads at most 2 MiB plus one byte to detect oversized requests. It sanitizes the filename to its final path component, validates the extension and content, and returns explicit HTTP errors for unsupported formats, invalid text and size violations.

Phase 2 — Text normalization and chunking

UTF-8 text is decoded with BOM support, line endings are normalized and surrounding whitespace is removed. The chunker creates overlapping segments using a default 900-character window and 120-character overlap.

Phase 3 — Transactional metadata and chunk storage

The store generates a UUID document identifier, calculates a SHA-256 digest from the uploaded bytes, records an ISO-8601 UTC timestamp and persists metadata and chunk rows in SQLite. The API returns the document identifier and chunk count.

Phase 4 — Deterministic keyword retrieval

The query is lowercased and tokenized into unique alphanumeric terms of at least two characters. Each chunk receives a score equal to the total case-insensitive occurrence count of those terms. Results are ordered by descending score, then filename and chunk index, and limited to the requested range of 1–50.

07. Engineering Decisions & Trade-offs

Local-first persistence

SQLite keeps the first implementation self-contained and easy to run. It is not a distributed or multi-tenant storage design.

Lexical matching first

Occurrence-based keyword scoring is transparent and deterministic. It does not capture synonyms, semantic similarity or contextual meaning.

Bounded upload surface

Restricting file types, encoding and upload size keeps the ingestion contract explicit while richer parsers remain future work.

Source traceability

Search responses include document IDs, filenames and chunk indexes to connect each result to its stored source.

Separate future agents

Knowledge-graph and recommendation modules are retained as explicit extension points, but they do not report successful work before implementation exists.

Prototype boundary

The current service has no authentication, per-user authorization, tenant isolation, LLM answer generation or external knowledge connectors.

09. Scope, Limitations & Security Boundaries

What the implementation does

  • Accepts UTF-8 .txt and .md documents up to 2 MiB.
  • Creates overlapping text chunks and stores them with document metadata in SQLite.
  • Performs deterministic keyword occurrence scoring and returns ranked matching excerpts.
  • Provides API access to document metadata and application health.

What it does not currently do

  • It does not parse PDF or DOCX files.
  • It does not use embeddings, vector databases or semantic retrieval.
  • It does not generate LLM answers or integrate Amazon Bedrock or S3.
  • It does not construct a knowledge graph or implement recommendations.
  • It does not provide authentication, per-user authorization, tenant isolation or production access controls.
  • It does not provide a production deployment or verified container runtime.
This is a local-first engineering prototype, not a production enterprise knowledge service or a RAG system. The search score is a lexical occurrence count, not a confidence score or semantic relevance measure. Do not expose the unauthenticated API to untrusted networks or use it as a multi-user document service.

10. Results & Engineering Learnings

The project establishes a working document-to-retrieval baseline with explicit input boundaries, chunk-level persistence and traceable keyword results. Its main engineering outcome is the end-to-end connection between upload validation, text preparation, transactional storage and deterministic retrieval behind a small API.

  • File validation and explicit error responses make ingestion behaviour predictable.
  • Chunk overlap provides continuity between adjacent text segments without requiring a vector index.
  • Persisting document identifiers and chunk metadata supports source traceability.
  • Deterministic lexical scoring provides a transparent baseline that can later be compared with semantic retrieval.
  • Keeping future graph and recommendation modules explicitly unimplemented avoids presenting placeholders as working capabilities.

Future increments could introduce additional document formats, embedding generation, vector retrieval, answer generation, identity controls and cloud storage. Each would require its own implementation, tests and evidence before being represented as an available capability.

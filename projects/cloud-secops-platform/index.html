CloudSecOps Platform: Evidence-Driven Security Assessment

A modular CloudSecOps prototype that turns caller-supplied infrastructure configuration, dependency declarations, security events and control outcomes into a structured security assessment. Four focused analysis agents feed a FastAPI workflow that aggregates findings, severity counts, recommendations and a bounded risk score.

01. Project Overview

CloudSecOps Platform is an evidence-driven security assessment prototype. It accepts a structured description of a resource and evaluates only the evidence included in that request. Its purpose is to demonstrate how security checks can be separated into focused components, orchestrated through an API and returned as a consistent assessment rather than a collection of unrelated scripts.

The workflow coordinates four analysis agents: configuration security, dependency-rule analysis, security-event pattern detection and compliance-control evaluation. A central workflow normalizes and aggregates their findings into a single response.

Project objectives

  • Define a typed request contract for resource configuration, package versions, event records and control outcomes.
  • Separate security analysis into independently understandable agent components.
  • Normalize findings with severity, evidence, description, source and remediation guidance.
  • Aggregate agent outputs into a bounded risk score and an overall assessment status.
  • Expose the workflow through a small FastAPI service with health and rule-discovery endpoints.
  • Package the service in a hardened, non-root Docker container.

Prototype · Local validation The application was tested locally and in a Docker container. No cloud account or live infrastructure is queried or modified by the current implementation.

02. Problem Definition

Cloud security assessments often draw on different kinds of evidence: configuration settings, software dependencies, operational events and control checks. When each check is implemented independently, it can be difficult to present a consistent view of findings, severity, evidence and recommended action.

Fragmented evidence

Configuration, package, event and control observations arrive in different shapes and need a common assessment structure.

Inconsistent findings

Without a shared finding model, severity, evidence and remediation guidance can vary across individual checks.

Orchestration requirement

Independent analysis components need a clear execution path and one response contract for API consumers.

Assessment boundaries

Missing evidence must not be interpreted as proof of security. The workflow distinguishes an unassessed resource from one with no issues detected in the checks performed.

03. Architecture & System Design

The implementation uses a synchronous request/response workflow. FastAPI validates the incoming payload with Pydantic, the workflow invokes the four analysis components, and their results are combined into a structured response.

API surface

  • GET /health returns service health status.
  • GET /secops/rules describes the configuration checks, event patterns, compliance controls and illustrative package catalogue.
  • POST /secops/scan accepts resource evidence and returns the aggregated assessment.
  • FastAPI provides interactive API documentation at /docs.

04. Analysis Agents

SecurityScanAgent — configuration analysis

Evaluates explicitly supplied flags for public access, encryption, logging and MFA. It creates findings only when a relevant setting is present and indicates a risky state; missing or null settings are not silently treated as secure or insecure.

VulnerabilityAgent — dependency rule analysis

Checks package names and versions against a small local illustrative catalogue. The current examples cover legacy release lines for Django, Flask and Requests. This is a deterministic demonstration rule set, not a live CVE feed, vulnerability database or exploitability assessment.

ThreatDetectionAgent — event pattern analysis

Inspects supplied event records for failed login/authentication outcomes and privilege-escalation or policy-change event types. These are deterministic patterns over request data, not machine-learning detection, behavioural analytics or live SIEM ingestion.

ComplianceAgent — control evaluation

Evaluates supplied outcomes for encryption at rest, audit logging, least privilege and MFA. Explicit false values create findings; missing or null control values remain unassessed. The result is a technical control check, not formal compliance certification.

06. Implementation Walkthrough

Phase 1 — Typed evidence contract

ScanRequest accepts a resource identifier and type, a configuration dictionary, a package-to-version dictionary, a bounded list of event records and a dictionary of compliance control outcomes. Unknown top-level fields are rejected. The response model defines findings, agent results, severity summaries, overall status and limitations.

Phase 2 — Independent analysis components

Each agent receives the normalized request data and returns an AgentResult containing its status, findings and number of checks performed. Shared finding helpers keep the finding shape and per-agent status logic consistent.

Phase 3 — Workflow aggregation

SecOpsWorkflow invokes the four agents, combines their findings, counts severities and calculates a bounded score. Severity weights are critical 40, high 25, medium 15, low 5 and informational 0; the aggregate is capped at 100. Overall status prioritizes critical findings, then high-risk findings, then review-required findings. With no findings and no checks performed, the result is not_assessed.

Phase 4 — API and container delivery

The FastAPI router exposes the workflow without coupling API handlers to individual agent implementations. The Dockerfile creates a system user, installs pinned dependencies, copies the application and runs Uvicorn as that non-root user. The runtime was started with a read-only root filesystem, a restricted temporary filesystem, dropped Linux capabilities and no-new-privileges.

07. Engineering Decisions & Trade-offs

Evidence-first assessment

Only supplied values are evaluated. Missing configuration or control data is left unassessed rather than converted into a clean result.

Deterministic local rules

Local rules keep behaviour reproducible and testable. They are deliberately not presented as live threat intelligence or authoritative vulnerability coverage.

Shared finding contract

A common schema makes findings from different agents easier to aggregate, test, display and extend.

Bounded risk score

Severity weights provide a simple prioritisation indicator. The score is not a probability of compromise or a calibrated enterprise risk metric.

Non-root container

The service runs as an unprivileged user, with read-only filesystem and capability restrictions applied at runtime to reduce container privileges.

Prototype boundary

The current service is stateless and request-driven. Cloud connectors, identity controls, persistence and production operational controls are not part of this implementation.

09. Scope, Limitations & Security Boundaries

What the implementation does

  • Analyses only configuration, package, event and control evidence supplied in the request.
  • Applies deterministic local checks and returns structured findings with evidence and recommendations.
  • Aggregates results from four independent analysis components.
  • Runs as a locally containerised API service.

What it does not currently do

  • It does not connect to or inspect AWS, Azure, GCP, Kubernetes or SIEM environments.
  • It does not retrieve live CVEs, threat feeds or vulnerability intelligence.
  • It does not use a trained AI model or behavioural analytics for event detection.
  • It does not provide formal compliance certification or independent audit evidence.
  • It does not include API authentication, authorization, tenant isolation, rate limiting or persistent audit storage.
  • It should not be exposed to the public internet or supplied with credentials, secrets or sensitive production logs.
This is a deterministic engineering prototype, not a production security product. Its risk score is a prioritisation aid based on supplied evidence, not a probability of compromise. No cloud resources were provisioned, scanned or changed by this project.

10. Results & Engineering Learnings

The project establishes a modular pattern for bringing heterogeneous security evidence into a common assessment workflow. Its strongest engineering outcome is the separation between evidence contracts, focused analysis components, shared finding models and central aggregation.

  • Typed request models make the evidence expected by each analysis path explicit and reject malformed top-level input.
  • Independent agents make checks easier to reason about and test in isolation.
  • Shared finding structures make aggregation and API responses predictable.
  • Explicit unassessed states prevent missing data from being mistaken for a secure result.
  • Container hardening can be incorporated into a small API prototype without claiming a production deployment.

Future engineering iterations could add carefully scoped cloud evidence adapters, maintained vulnerability intelligence, authenticated API access, durable audit records, richer event normalization and integration tests. Those are future directions, not capabilities of the current version.

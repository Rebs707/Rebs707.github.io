Enterprise VCP to AWS Migration Simulation

An infrastructure and operations simulation of a Versa Controller Platform migration to AWS. The project combines Terraform-provisioned networking and compute, scripted migration and branch-onboarding workflows, validation state, CloudWatch alarms, incident classification and operator runbooks.

01. Project Overview

This project models the operational work involved in moving a centrally managed SD-WAN controller environment from an on-premises Versa Controller Platform (VCP) context to an AWS-hosted target environment. It establishes a simulated legacy baseline, provisions a representative AWS network and controller endpoint, and documents the migration lifecycle from readiness checks through incident handling and rollback planning.

The implementation is intentionally a simulation. The EC2 instance is a representative controller endpoint running Nginx and serving a static health page; it is not the Versa controller software. The migration and branch workflows model process stages and state transitions rather than transferring live controller configuration or establishing real branch tunnels.

Project objectives

  • Define a representative AWS target network using Terraform.
  • Provision public and private subnets, routing, security groups, an EC2 simulation endpoint and an Application Load Balancer.
  • Model pre-migration validation, migration execution and branch onboarding as scripted workflows.
  • Record workflow state and timestamped logs for operational traceability.
  • Configure CloudWatch alarms and document post-migration checks.
  • Exercise incident classifications and document recovery and rollback procedures.

Simulation scope Infrastructure is described from the Terraform configuration; workflow behaviour is described from the Bash scripts and runbooks. No claim is made here that a live VCP platform or production branch network was migrated.

02. Problem Definition

A controller migration is not only a compute relocation. It involves understanding the existing management-plane context, preparing network and access dependencies, coordinating migration and branch onboarding, validating service health, and defining how operators respond when expected conditions are not met.

Source context

The documented legacy model includes a centrally managed, on-premises multi-tenant VCP, branch offices, corporate WAN connectivity, TACACS administrator authentication and existing routing policies.

Target representation

The Terraform configuration provisions an AWS VPC with public/private subnet tiers, internet and NAT routing, security groups, a private EC2 simulation controller and a public-facing ALB.

Operational challenge

Migration readiness, controller availability, branch onboarding, connectivity validation and recovery decisions need explicit stages, state records and operator procedures.

Simulation success criteria

Workflow state files and validation counters represent process outcomes. Infrastructure configuration and alarm definitions provide a target environment model; they do not by themselves prove a successful live migration.

The ALB security group allows inbound TCP 80 and 443, but the inspected configuration defines only an HTTP listener on port 80. No HTTPS listener or certificate is configured in this Terraform file. The controller security group allows TCP 80 only from the ALB security group.

Network and compute components

  • VPC: 10.0.0.0/16, with DNS support and DNS hostnames enabled.
  • Public subnets: 10.0.1.0/24 and 10.0.2.0/24, with public IP assignment enabled and a default route through the Internet Gateway.
  • Private subnets: 10.0.11.0/24 and 10.0.12.0/24, associated with a private route table whose default route uses the NAT Gateway.
  • NAT: One Elastic IP and one NAT Gateway in the first public subnet.
  • Controller: One t3.micro EC2 instance in the first private subnet, with no public IP, an instance profile for Systems Manager core access, IMDSv2 required and an encrypted 8 GB gp3 root volume.
  • Load balancing: An internet-facing Application Load Balancer spans both public subnets and forwards HTTP traffic to an instance target group on port 80.
  • Monitoring: CloudWatch alarms cover EC2 CPU utilization above 80%, EC2 status-check failure and ALB unhealthy-host count.

Management-plane simulation boundary

The EC2 user-data installs and starts Nginx and writes a simple page containing “VCP AWS Controller Simulation” and “Controller status: healthy”. This provides a representative HTTP endpoint for the target group; it does not run Versa controller services or reproduce real VCP APIs, configuration transfer, TACACS integration or SD-WAN control tunnels.

05. Implementation Walkthrough

Phase 1 — Infrastructure provisioning

Terraform defines the VPC, two public and two private subnets, Internet Gateway, public and private route tables, one NAT Gateway, security groups, IAM role/profile, EC2 simulation controller, ALB, target group, listener and three CloudWatch alarms. The Amazon Linux 2023 AMI is resolved through the public SSM parameter for the latest x86_64 kernel-default image.

Phase 2 — Pre-migration readiness

pre_migration_validation.sh checks for Terraform, Git and Python 3; checks AWS CLI and caller identity when the CLI is present; verifies required Terraform and architecture files; runs terraform fmt -check and terraform validate; and warns if the Git working tree has changes. It reports PASS/WARN/FAIL counts and exits non-zero when failures are recorded. Missing or invalid AWS credentials are a warning in the script, not a blocking failure.

Phase 3 — Migration workflow simulation

migrate_controller.sh models five sequential stages: prerequisite validation, AWS controller configuration preparation, simulated configuration transfer, simulated reachability validation and readiness for branch onboarding. It generates a migration ID, UTC timestamped log and state file under logs/migrations/ and state/migrations/. A FAIL_AT_STEP variable supports injected failure scenarios.

Phase 4 — Branch onboarding simulation

onboard_branch.sh checks for a successful migration state, then models branch registration, controller reachability, control-tunnel establishment, routing validation and operational confirmation. BRANCH_ID, CONTROLLER_URL and FAIL_AT_STEP parameterise the workflow. Branch-specific state and logs are written under state/onboarding/ and logs/onboarding/.

Phase 5 — Post-migration validation

post_migration_validation.sh evaluates migration state and branch onboarding state, then records simulated ALB health, controller reachability and branch connectivity checks. It counts PASS/WARN/FAIL results and writes a timestamped validation log and state record. A connectivity degradation is represented as a warning; configured failure injections for other checks produce failed validation.

Phase 6 — Incident and recovery workflows

simulate_incident.sh classifies five scenarios and records severity, impact, recommended action and outcome in incident state files: controller unreachable, branch onboarding failure, ALB unhealthy, partial connectivity and rollback required. The runbooks describe operator actions for controller-unreachable handling and restoration of the previous VCP configuration after a service-impacting change.

06. Engineering Decisions & Trade-offs

Private controller placement

Choice: Place the EC2 simulation controller in a private subnet without a public IP. Trade-off: Inbound application traffic is mediated by the ALB; outbound private-subnet access depends on NAT.

Single NAT Gateway

Choice: Use one NAT Gateway in the first public subnet for both private subnet routes. Trade-off: This is simpler and less costly for a simulation, but creates an AZ and availability dependency and may introduce cross-AZ data transfer.

One controller instance

Choice: Use one t3.micro controller simulation instance. Trade-off: The ALB spans two public subnets, but the single target does not provide controller-level high availability.

HTTP-only listener

Choice: Configure an HTTP listener on port 80 and an HTTP target group. Trade-off: This keeps the simulation straightforward; TLS termination and certificate management are not implemented in the inspected configuration.

File-based workflow state

Choice: Store migration, onboarding, validation and incident outcomes in readable state files with timestamped logs. Trade-off: This supports a lightweight local simulation, but does not provide distributed locking, durable central state or concurrent workflow coordination.

Simulated workflow stages

Choice: Model process stages without invoking live VCP or branch APIs. Trade-off: This makes lifecycle and failure-path logic demonstrable while keeping the boundary between workflow modelling and real migration explicit.

07. Failure Scenarios & Operational Response

The incident script records a classification and recommended response. The accompanying runbooks describe operator procedures. These are simulated decision paths; the script does not perform the remediation actions itself.

Controller unreachable

Classification: HIGH · RESCHEDULE. Request console access from the field engineer, keep the VCP platform unchanged and resume onboarding after access is restored. The runbook explicitly states rollback is not required for this case.

Branch onboarding failure

Classification: MEDIUM · FAILED. The simulated impact is a single unavailable branch; the recorded action is to investigate onboarding.

ALB target unhealthy

Classification: HIGH · FAILED. The recorded action is to validate target health; the simulation marks controller service availability as unconfirmed.

Partial connectivity

Classification: MEDIUM · PARTIAL. Investigate routing and assess impact before making a rollback decision.

Rollback required

Classification: CRITICAL · ROLLBACK. Stop further onboarding, restore the previous VCP configuration, validate recovery, record the outcome and prepare the required issue report.

The rollback runbook documents restoration steps but the incident script only writes an outcome of ROLLBACK and an action label. No automated VCP configuration restoration is implemented in that script.

08. Testing & Validation

The repository contains validation logic and failure-injection controls. The code establishes what the scripts are designed to check; it is not, by itself, evidence that each check was executed successfully in a deployed AWS environment.

Local readiness checks

The pre-migration script checks tool availability, AWS caller identity when possible, required files, Terraform formatting and Terraform configuration validation, plus Git working-tree status.

Workflow state checks

Migration and branch onboarding write state files. Post-migration validation reads those files and records pass, warning and failure totals.

Failure injection

FAIL_AT_STEP is present in migration and onboarding scripts. FAIL_CHECK in post-migration validation can inject migration, branch, ALB, controller or connectivity outcomes.

Infrastructure monitoring definitions

Terraform declares alarms for EC2 CPU above 80%, EC2 status-check failure and ALB unhealthy-host count. Alarm definitions are not evidence of observed alarm firing.

Implementation review notes

  • The migration and onboarding scripts use set -uo pipefail, but not set -e. Their ERR traps alone do not guarantee that a failing function call in the straight-line workflow stops subsequent steps. Explicit error handling or set -e with carefully tested control flow would make failure propagation more reliable.
  • The scripts select the “latest” migration state using a filename sort and tail -1. Lexicographic ordering of timestamped IDs is not a robust substitute for explicitly comparing modification times or parsed timestamps.
  • The post-migration script labels ALB health, controller reachability and branch connectivity as simulated checks; they do not call AWS APIs or probe a network endpoint.
  • The pre-migration script treats unavailable or invalid AWS credentials as a warning. The runbook's success criteria separately require AWS access to be confirmed before real deployment.
No deployment screenshots, Terraform apply output, actual AWS resource inventory, script execution logs or measured test results were available in the reviewed material. Those results are therefore not asserted in this case study.

09. Results & Engineering Learnings

What the repository demonstrates

  • A Terraform-defined AWS network and application entry path with public/private subnet separation, routing, security controls, a private EC2 endpoint, ALB and CloudWatch alarm definitions.
  • A staged migration and branch-onboarding workflow model with parameterised identifiers, local state files and timestamped logs.
  • A post-migration validation model that aggregates pass, warning and failure outcomes.
  • A five-scenario incident classification model and operator runbooks for readiness, migration, onboarding, validation, controller-unreachable response and rollback.

Engineering learnings

  • Migration planning needs explicit separation between infrastructure readiness, workflow execution, service validation and operational recovery.
  • Private subnet placement, load-balancer health checks and security-group references are useful building blocks, but high availability depends on the number and placement of actual targets and network dependencies.
  • State and logs improve traceability, while reliable orchestration also requires correct failure propagation, robust state selection and safe handling of concurrent runs.
  • Operational runbooks should distinguish between rescheduling, investigation and rollback; not every connectivity issue requires reverting the migration.
  • Simulation boundaries should be explicit so that modeled outcomes are not mistaken for production integrations or live service validation.

AWS ECS Production Application: From Container to Release Validation

A containerized Flask service with hardened Docker runtime, Terraform-defined ECS infrastructure, automated CI checks and a tested local release rollback path.

This project brings application delivery, container security, infrastructure as code and release validation into one engineering workflow. The repository demonstrates a validated application and infrastructure configuration, plus a local Docker deployment simulation. AWS provisioning and live production deployment have not been performed; the case study keeps that boundary explicit.

01 / Project Overview

What the project demonstrates

An end-to-end delivery path that connects application behaviour, container packaging, infrastructure definition and release verification.

Application service

A small Flask service exposes a root response and a dedicated JSON health endpoint, served through Gunicorn on port 5001.

Container engineering

A Python 3.13 slim image runs as a non-root user, includes a container health check and uses a reduced runtime dependency set.

Infrastructure definition

Terraform describes an ECR repository, ECS Fargate cluster and service, load balancer, security groups and CloudWatch log group.

Release validation

GitHub Actions validates application tests, Docker image build and Terraform configuration. A local Docker script exercises candidate health checks and rollback.

04 / Implementation

From application to release checks

01 · Application and tests

Implemented a compact Flask service with a root route and JSON health route. The pytest suite covers successful responses, health payload and not-found behaviour.

02 · Container build

Built the service into a Python slim image, installed pinned runtime dependencies, switched to a dedicated non-root user and added a container-level health check.

03 · Runtime hardening

Verified the application in a read-only root filesystem with a writable temporary filesystem, dropped Linux capabilities and no-new-privileges enabled.

04 · Infrastructure as code

Defined ECR, ECS Fargate, ALB, security groups, CloudWatch logging and an ECS deployment circuit breaker with rollback in Terraform.

05 · CI validation

GitHub Actions runs application tests, builds the Docker image and checks Terraform formatting, initialization and validation. The workflow validates; it does not publish an image or deploy AWS.

06 · Local release simulation

A Docker release script checks a candidate container's health and restores the previous image when a controlled failure is introduced. This is a local simulation, not an ECS deployment.

06 / Release & Recovery

Health-checked local rollback

The release script is deliberately scoped to local Docker containers to exercise candidate validation and recovery behaviour.

Candidate validation

The script checks that the candidate image exists, starts a container and polls the health endpoint. An unhealthy candidate is removed rather than retained as the active release.

Previous-version recovery

A controlled failure test demonstrated restoration of the previous v3 image and a healthy endpoint after the candidate failed its health check.

The local script removes the existing container before starting the candidate. It therefore has deployment downtime and is not a zero-downtime release strategy. ECS deployment behaviour is separately represented by the Terraform circuit-breaker configuration and has not been exercised in AWS.
07 / Engineering Decisions

Trade-offs and next production steps

Small, hardened runtime image

A slim base and non-root user reduce unnecessary runtime surface. The read-only filesystem and capability restrictions add defence in depth, while requiring explicit writable paths.

Immutable ECR tags

Immutable tags and image scanning support traceable releases and vulnerability visibility. The CI workflow currently builds but does not push images to ECR.

Supplied network and IAM dependencies

Terraform accepts an existing VPC, public subnets and task execution role rather than creating all account-level prerequisites. Deployment requires validating those dependencies and permissions.

Production hardening still required

Before serving real traffic, add HTTPS and certificate management, review private-subnet placement and egress, consider at least two tasks for availability, and validate logging, alarms and deployment behaviour in AWS.

08 / Deployment Boundary

What is—and is not—deployed

Verified in the project

  • Application test suite and GitHub Actions validation
  • Docker image build and hardened local runtime
  • Terraform formatting and static validation
  • Local Docker release and controlled rollback simulation

Not yet verified in AWS

  • No ECS, ECR, ALB or CloudWatch resources were provisioned
  • No AWS service endpoint or live application URL exists
  • No image publication or AWS deployment pipeline is configured
  • Production networking, HTTPS and live rollback remain untested
AWS provisioning was not performed in the KodeKloud sandbox because an eligible ECS task execution role was unavailable and IAM role creation was denied. Terraform was validated locally. This portfolio page does not claim a live AWS or production deployment.
